# Как устроена реализация лабораторной работы

Документ подробно объясняет, как программы A, B и C выполняют пункты задания и
почему в коде используются именно эти решения. В каждом разделе есть ссылки на
функции исходников. Код здесь не дублируется: по ссылке открывается место, где
реализована описанная логика.

Проект рассчитан на Linux и C++17. Варианты задания для Windows и дополнительные
необязательные пункты отмечены отдельно.

## Сборка и запуск

Из каталога проекта соберите программы:

    cmake -S . -B build
    cmake --build build

Для полной демонстрации откройте два терминала. В первом запустите программу C:

    ./build/program_c

Во втором запустите программу B:

    ./build/program_b

В B введите текст, цвет и размер, запустите A, затем отправляйте команды через
меню. В отдельном окне A можно нажимать клавиши напрямую. Чтобы завершить C,
введите q и нажмите Enter.

## Программа A

### 1. A работает в цикле событий

Главная задача A — оставаться работающей и ждать следующее событие. В
[run_event_loop()](program_a.cpp#L330) функция poll() ожидает готовность сразу
двух файловых дескрипторов: стандартного ввода терминала и FIFO. Таймаут равен
-1, поэтому цикл не опрашивает источники постоянно и не тратит процессорное
время, пока событий нет. Когда готов один из дескрипторов, A вызывает его
обработчик и затем возвращается к poll().

Для чтения клавиш терминал перед этим переводится в неканонический режим:
[enable_keyboard_mode()](program_a.cpp#L244) отключает ожидание Enter и эхо
символов. Поэтому [read_keyboard()](program_a.cpp#L283) может получить один
символ сразу после нажатия. Изначальные настройки терминала восстанавливаются
при завершении в [main()](program_a.cpp#L367), чтобы приглашение оболочки снова
работало нормально.

Вывод выполняет [draw_text()](program_a.cpp#L134). ANSI-коды очищают экран,
перемещают курсор в начало и выбирают цвет текста; после отображения цвет
терминала сбрасывается. Так вывод не зависит от графической библиотеки и
обновляется непосредственно в консоли.

На сигналы SIGINT и SIGTERM установлен обработчик [request_stop()](program_a.cpp#L34).
Он только выставляет флаг остановки. Терминал, FIFO и журнал освобождаются
основным циклом, а не внутри обработчика сигнала: это позволяет завершить
обычную очистку ресурсов. Вариант задания с окном Win32 и WM_KEYDOWN здесь не
реализован, потому что проект сделан для Linux.

### 2. A меняет отображение по клавишам

Клавиатурный символ преобразуется в действие в
[apply_key()](program_a.cpp#L145). Клавиши 1, 2, 3 и 4 выбирают красный,
зелёный, синий и жёлтый цвета. Клавиша + вызывает [next_color()](program_a.cpp#L77),
которая выбирает следующий цвет в цикле: red → green → blue → yellow → magenta
→ red. Клавиша t сразу выбирает magenta, а q меняет флаг running, по которому
основной цикл понимает, что пора завершиться.

После распознавания клавиши [handle_key()](program_a.cpp#L159) записывает
событие в журнал. Если цвет изменился, она вызывает перерисовку. Для q экран
повторно не рисуется: действие этой клавиши — завершение работы. Для неизвестной
клавиши apply_key() возвращает признак отсутствия действия, поэтому она не
меняет состояние и не создаёт запись о поддерживаемом событии.

Так обработка одной клавиши отделена от ожидания ввода. Тот же handle_key()
позже используется для команд FIFO, поэтому клавиатура и B могут менять цвет
одинаковым способом.

### 3. Параметры A задают начальное состояние

В [ProgramState](program_a.cpp#L24) собраны данные, которыми программа пользуется
после запуска: отображаемый текст, количество его повторений, цвет и флаг
работы. Инициализаторы задают значения по умолчанию: Hello, green и размер 1.
Если B или пользователь передаст параметры, они заменят эти начальные значения.

[parse_arguments()](program_a.cpp#L88) обходит массив argc/argv парами
«параметр — значение». Это ручной разбор командной строки, без сторонней
библиотеки. Поддерживаются --text, --color и --size. Параметр без следующего
значения, неизвестный ключ или неверное значение приводят к сообщению об
ошибке до начала интерактивного цикла.

Название цвета проверяет [parse_color()](program_a.cpp#L38). Размер разбирается
как целое число и должен быть больше нуля. Благодаря проверке программа не
начинает вывод с неподдерживаемым цветом или бессмысленным количеством
повторений. Если параметр не указан, значение структуры остаётся значением
по умолчанию.

### 4. A дописывает журнал событий

Файл program_a.log открывается в [main()](program_a.cpp#L367) в режиме добавления.
Поэтому новый запуск не стирает историю предыдущего. Время и само событие
форматирует [log_event()](program_a.cpp#L123): временная метка записывается в
местном времени с точностью до секунды, после строки выполняется flush.

Перед началом цикла main() пишет событие start с начальным цветом. При
завершении цикла пишется exit. Между ними [handle_key()](program_a.cpp#L159)
добавляет записи key= для обработанных клавиш, а
[handle_fifo_line()](program_a.cpp#L171) регистрирует допустимые команды
из FIFO. В журнале A клавиши с клавиатуры и команды key= из FIFO имеют
одинаковый формат. По этой причине программа C видит, что произошло, но не
может определить источник клавиши.

Журнал нужен не только как история для пользователя. Программа C читает его
позже и использует временные метки A при записи наблюдаемых событий.

### 5. A получает команды из FIFO

FIFO — именованный канал, через который B и C могут передать строку процессу A.
Функция [prepare_fifo()](program_a.cpp#L196) проверяет путь
/tmp/program_a_fifo. Если FIFO уже есть, она убеждается, что это именно
именованный канал; если его нет, создаёт его с помощью mkfifo().

[open_fifo()](program_a.cpp#L221) открывает канал с O_NONBLOCK, чтобы отсутствие
пишущего процесса не заставляло A зависнуть во время запуска. Для чтения
используется O_RDWR: собственный конец записи предотвращает EOF и постоянные
срабатывания poll(), когда внешнего отправителя пока нет. После завершения
[close_fifo()](program_a.cpp#L237) закрывает дескриптор. FIFO удаляется только
в том случае, если его создала эта копия A; ранее существовавший файл она
оставляет.

Чтение выполняет [read_fifo()](program_a.cpp#L301). Данные из FIFO не обязаны
поступить одним системным вызовом: поэтому функция накапливает их в
pending_line и ждёт символа новой строки. Готовые строки передаются
[handle_fifo_line()](program_a.cpp#L171). Команда key=1 превращается в клавишу 1
и направляется в handle_key(); команда cmd=color:blue непосредственно задаёт
цвет. Таким образом, источники управления разные, но изменение клавиши
обрабатывается одним общим кодом.

Команды передаются строками, потому что FIFO — поток байтов и границы между
отдельными write() сами по себе не являются границами сообщений. Windows-вариант
с WM_COPYDATA или PostMessage не реализован.

## Программа B

### 6. B вводит параметры и команду через меню

Структура [Parameters](program_b.cpp#L13) хранит значения, которые B затем
передаст A: текст, цвет и размер. В
[read_parameters()](program_b.cpp#L47) пользователь вводит их по очереди с
подсказками. Цвет проверяется функцией is_supported_color(), а число повторений
— parse_size(). Параметры сохраняются только после успешной проверки целого
набора. Если ввод неправильный, прежние значения сохраняются, а меню
продолжает работать.

Меню отображается функцией [show_menu()](program_b.cpp#L267). Пункт отправки
команды вызывает [prompt_and_send_command()](program_b.cpp#L253), которая
получает строку от пользователя и проверяет её прежде, чем обращаться к FIFO.
Основной цикл [main()](program_b.cpp#L277) после каждого действия показывает
меню снова. Это позволяет менять параметры, запускать A и отправлять несколько
команд за один сеанс B.

В задании допускается простой последовательный консольный ввод. Поэтому здесь
нет полей графического окна, GTK, Qt или сторонних зависимостей.

### 7. B запускает A и передаёт ей параметры

Функция [find_program_a()](program_b.cpp#L78) читает путь к исполняемому файлу
самой B через /proc/self/exe и заменяет имя B на program_a. A ищется рядом с B:
это позволяет запускать проект из сборочной папки, не полагаясь на текущий
каталог пользователя. Доступность A проверяется до создания дочернего процесса.

[launch_program_a()](program_b.cpp#L128) сначала проверяет, не работает ли A уже
и не открывается ли её окно. Это важно из-за общего FIFO: две копии A могли бы
одновременно читать одну команду, и B не могла бы надёжно выбрать получателя.
Затем fork() создаёт дочерний процесс. В дочернем процессе execvp() запускает
Ptyxis, который открывает отдельный терминал для A. Отдельный терминал нужен,
чтобы A самостоятельно принимала клавиатурные команды и B независимо
продолжала показывать меню.

Аргументы --text, --color и --size передаются как отдельные элементы массива
execvp(), а не как текст shell-команды. Это сохраняет границы значений
параметров и не требует экранировать пробелы в тексте. A получает эти аргументы
обычным способом через argc/argv и устанавливает начальное состояние до
отрисовки.

[reap_terminals()](program_b.cpp#L99) периодически вызывает
waitpid(..., WNOHANG), чтобы собирать завершённый процесс терминала, не блокируя
меню. [program_a_is_running()](program_b.cpp#L114) проверяет наличие читающей
стороны FIFO. Вместе эти проверки помогают отличить работающую A от окна
терминала, которое ещё запускается или уже завершилось.

Терминал в этой версии задан путём /usr/bin/ptyxis. Windows-вариант CreateProcess
не добавлен.

### 8. B отправляет команду A

Сначала [is_supported_command()](program_b.cpp#L194) сравнивает введённую строку
с разрешённым набором key=1, key=2, key=3, key=4, key=+, key=t, key=q и
cmd=color:<цвет>. Это предотвращает отправку случайной строки, которую A не
понимает.

[send_command()](program_b.cpp#L208) проверяет, что /tmp/program_a_fifo
существует и является FIFO. Затем он открывает его с O_WRONLY | O_NONBLOCK.
Неблокирующий режим нужен, чтобы B не зависла при отсутствии читающей A.
После этого команда записывается с символом новой строки, который сообщает A,
что строка завершена, и файловый дескриптор закрывается.

На стороне A строку принимает [read_fifo()](program_a.cpp#L301), затем
[handle_fifo_line()](program_a.cpp#L171). key-команда передаётся в тот же
handle_key(), что и клавиатурный ввод, поэтому B не реализует отдельный набор
правил смены цвета.

В B игнорируется SIGPIPE. Если A закроется между проверкой FIFO и записью,
write() может вернуть EPIPE; B ловит эту ситуацию и выводит сообщение вместо
аварийного завершения. Вариант с PostMessage/WM_COPYDATA относится к Windows и
не реализован.

### 9. B сообщает об ошибках и продолжает работу

При поиске A [find_program_a()](program_b.cpp#L78) объясняет, если рядом нет
исполняемого файла. [launch_program_a()](program_b.cpp#L128) проверяет наличие
Ptyxis и результат fork(); если execvp() не сработал, дочерний процесс выводит
ошибку и завершает себя с кодом 127. B позднее получает этот статус через
reap_terminals().

При отправке команды [send_command()](program_b.cpp#L208) различает несколько
ситуаций: путь отсутствует, путь не является FIFO, нет читателя, A завершилась
во время записи или произошла другая ошибка. Это помогает пользователю понять,
что именно нужно исправить. Отправка выполняется неблокирующе, поэтому B не
застревает в ожидании A.

Ошибочное действие не завершает основное меню. Функция main() продолжает цикл
и снова предлагает выбрать пункт. Это позволяет, например, поправить
параметры или повторить отправку после запуска A.

## Программа C

### 10. C определяет именно процесс A

Функция [companion_program_a_path()](program_c.cpp#L59) вычисляет путь к A,
лежащей рядом с исполняемым файлом C. Затем
[find_program_a_processes()](program_c.cpp#L98) перебирает числовые каталоги
в /proc и проверяет кандидатов через is_program_a_process().

Проверка намеренно использует несколько признаков. В
[is_program_a_process()](program_c.cpp#L71) имя в /proc/<pid>/comm должно быть
точно program_a; первый аргумент из /proc/<pid>/cmdline также должен указывать
на program_a; исполняемый файл процесса из /proc/<pid>/exe сравнивается с
бинарным файлом A рядом с C по устройству и inode. Одной проверки имени было бы
недостаточно: другой процесс может иметь такое же короткое имя. Проверка
исполняемого файла уменьшает риск принять посторонний процесс за A.

B запускает Ptyxis, но C ищет не PID терминала. Она находит дочерний процесс A
по его собственным данным в /proc.

Условие для Windows предлагает EnumProcesses, GetModuleBaseName или FindWindow.
Эти API не применяются, поскольку реализация рассчитана на Linux.

### 11. C следит за журналом A и ведёт собственный журнал

В [MonitoredProgram](program_c.cpp#L21) хранятся PID наблюдаемой A, путь к её
журналу, позиция чтения и признаки уже записанных start/exit. Такой набор
позволяет продолжать чтение одного файла между итерациями цикла и не дублировать
события.

[attach_to_program_a()](program_c.cpp#L168) получает рабочий каталог процесса
из /proc/<pid>/cwd. Именно там A открывает program_a.log, поэтому C находит
правильный журнал даже тогда, когда её запустили из другого каталога.
[read_existing_start()](program_c.cpp#L135) просматривает существующий журнал,
чтобы найти время текущего запуска A. При подключении к уже работающей A
старые клавиши не воспроизводятся: позиция чтения устанавливается на конец уже
имеющихся полных строк.

После подключения [read_new_a_log_lines()](program_c.cpp#L268) периодически
читает только новые завершённые строки. Неполная строка не обрабатывается до
появления перевода строки, чтобы C не увидела запись в середине её добавления.
Если файл был усечён, позиция чтения сбрасывается к началу.

[handle_a_log_line()](program_c.cpp#L218) распознаёт start, exit, key= и
cmd=color:. События клавиш и цветовые команды переносятся в program_c.log с
временем из журнала A. Время инъекции или ошибки инъекции создаётся самой C.
Функция [write_event()](program_c.cpp#L42) добавляет строку и сразу сбрасывает
буфер, чтобы записи оставались на диске во время наблюдения.

### 12. C инъецирует key=t после key=+

Когда обработчик журнала [handle_a_log_line()](program_c.cpp#L218) видит новую
запись key=+, он вызывает [send_key_t()](program_c.cpp#L183). Эта функция ещё
раз ищет процессы A и проверяет, что ожидаемый PID всё ещё найден единственным.
Повторная проверка нужна, потому что между чтением записи журнала и отправкой
команды A могла завершиться или могла появиться вторая A.

Затем send_key_t() проверяет, что путь /tmp/program_a_fifo действительно
является FIFO, открывает его с O_WRONLY | O_NONBLOCK, записывает строку key=t
с переводом строки и закрывает файловый дескриптор. Если читателя уже нет,
операция завершается ошибкой, а C остаётся запущенной. SIGPIPE игнорируется в
main(), чтобы аварийное закрытие FIFO не завершило C.

В журнале A клавиатурный плюс и команда key=+ из B выглядят одинаково.
Следовательно, C реагирует на каждую новую запись key=+, независимо от
источника. Это ограничение текущего формата журнала.

### 13. C переживает отсутствие A, журнала или FIFO

Если A ещё не запущена, основной цикл в [main()](program_c.cpp#L333) сообщает
об ожидании и продолжает искать её каждые 200 мс. Если A найдена, C
подключается к её журналу. Если файл журнала пока отсутствует, функция
[read_new_a_log_lines()](program_c.cpp#L268) сообщает об ожидании файла и
повторяет проверку в следующих итерациях. Пустой журнал не считается ошибкой:
новых строк просто пока нет.

При отсутствии FIFO или читателя [send_key_t()](program_c.cpp#L183) возвращает
причину неудачи. C записывает её в собственный журнал и продолжает наблюдение.
Ошибки инъекции не останавливают процесс C.

Когда PID A исчезает, [finish_monitoring()](program_c.cpp#L299) сначала
пытается прочитать последние доступные строки журнала. Если там есть штатный
exit, C сохраняет его время. Если exit отсутствует, C записывает время, когда
она обнаружила исчезновение, и явно помечает его как обнаружение, а не точное
время завершения A. После этого состояние наблюдения сбрасывается, и C готова
найти следующий запуск.

Если одновременно найдены несколько подходящих процессов A, main() выводит
сообщение о неоднозначности и приостанавливает мониторинг. Это не позволяет
послать команду неизвестной копии A через общий FIFO.

### 14. Полный сценарий демонстрации

Сценарий проверяет, что три программы работают вместе, а не только по
отдельности.

1. В первом терминале запустите ./build/program_c. C сообщит, что ждёт A.
2. Во втором терминале запустите ./build/program_b.
3. В меню B выберите ввод параметров и задайте текст Hello, цвет green и размер 3.
4. В B запустите A. Она должна открыться в Ptyxis и вывести Hello три раза зелёным.
5. В B отправьте key=1. A должна показать текст красным, а журнал A должен получить key=1.
6. Отправьте key=+. A обработает плюс и запишет его в свой журнал. C увидит новую запись, зафиксирует её и отправит key=t. В результате A переключится на magenta.
7. Отправьте cmd=color:blue. A станет синей; событие появится в журнале A и будет скопировано в журнал C.
8. Нажмите q в окне A. A допишет exit и завершится; C должна сохранить завершение и вернуться к ожиданию следующего запуска.
9. Проверьте program_a.log в рабочем каталоге A и program_c.log в каталоге, откуда запущена C.

### 15. Сборка и поддерживаемые платформы

Файл [CMakeLists.txt](CMakeLists.txt#L1) объявляет три цели C++17: program_a,
program_b и program_c. Основные команды сборки и запуска также описаны в
[README.md](README.md#L6).

В коде используются Linux API: termios, poll, FIFO, fork/execvp и /proc.
Windows-реализация, конфигурация CMake для Visual Studio или MinGW, Makefile и
AutoIt-скрипт не добавлялись. Поэтому пункт о сборке под Windows этим проектом
не подтверждается; исходники и инструкции рассчитаны на Linux.

### 16. Дополнительный мониторинг (необязательный пункт)

Необязательное чтение /proc/<pid>/stat и /proc/<pid>/fd не добавлено.
Для идентификации A используются /proc/<pid>/comm, /proc/<pid>/cmdline и
/proc/<pid>/exe; путь к рабочему каталогу берётся из /proc/<pid>/cwd в
[attach_to_program_a()](program_c.cpp#L168).

SetWindowsHookEx относится к Windows и не применяется. ptrace также не
используется: для наблюдения достаточно доступных записей /proc и журнала A.
